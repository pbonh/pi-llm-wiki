---
description: Round-trip a completed Hermes kanban run back into the wiki as living documentation
argument-hint: "<task-id | run-id>"
---
Read `AGENTS.md` and follow the **Kanban Ingest** workflow to round-trip the Hermes run at `$1` back into the wiki.

**Preflight 1 (hard) — Hermes.** Invoke `hermes kanban assignees`. If `hermes` is not on `PATH` or the command fails, abort with the same install-hint message as `/wiki-kanban-emit`. Do not proceed without Hermes.

**Preflight 2 (hard) — board binding.** Run `scripts/check-prereqs.sh kanban_ingest --quiet --json` first to surface missing `board_bound` (or any other unsatisfied artifact) with the helper's hint. Then read `kanban/board.yaml` with `yq` and capture `board:`. If empty or `<!--` markers remain, abort with the `/wiki-kanban-board <slug>` hint. Pass `--board <slug>` on every subsequent `hermes kanban` invocation in this run (`show`, `runs`, `list`); without it, lookups fall through to the operator's currently-active board, which usually isn't this wiki's.

**Preflight 3 (hard) — git discipline.** Fetch the task's run metadata via `hermes kanban runs $1 --board <slug> --json` (the durable `task_runs` table — every attempt, oldest-first). For each completed run, read `metadata.branch_head` from the structured handoff. Then run `scripts/check-prereqs.sh kanban_ingest --branch-head <branch_head>` from the wiki root. The helper renders the `git:worker-branch-merged` check (`git fetch --quiet origin <trunk> && git merge-base --is-ancestor <branch_head> origin/<trunk>`) and fails with exit 3 when the worker's branch is not on trunk. On failure, print *"Run $1's branch <branch_head> is not on <trunk>; merge before ingesting."* plus the rendered `git merge-base` command, and abort. **Do not write any `## Implementation Evidence` section while the worker's branch is unmerged** — the wiki would record evidence pointing at code that is not yet trunk.

If `wiki/.pipeline.yaml` is absent, the manifest preflight exits 0 and ingest proceeds (back-compat). The `kanban/board.yaml` read and `--board <slug>` flag still apply — if the file is missing too, abort with the `/wiki-kanban-board` hint.

Steps (from AGENTS.md):
1. **Fetch attempt history.** `hermes kanban runs $1 --board <slug> --json` returns every run for the task, oldest-first. Walk all of them — not just the latest. Capture per run: `summary`, `verification`, `changed_files`, `residual_risk`, the [[concepts/structured-handoff]] payload, `metadata.branch_head`, plus `run_id` and `completed_at` from the run header.
2. **Validate the handoff schema.** Every run's `metadata` MUST contain the keys declared in `prompts/_handoff-schema.md`: `changed_files`, `verification`, `dependencies`, `blocked_reason`, `retry_notes`, `residual_risk`, `branch_head`, `wiki_spec`, `wiki_adr_ids`. Missing keys → abort with `missing keys: [...]`. Do not partially ingest.
3. **Sanitize metadata.** [[concepts/structured-handoff]] forbids tokens, OAuth material, raw logs, and unrelated transcripts. Copy summaries and pointers (file paths, commit hashes, run ids, URLs) — refuse to copy secrets or raw logs. If the metadata is dirty, surface the issue to the user and stop. Do not silently scrub-and-copy.
4. **Write per-attempt handoff JSON files (hard).** For each completed run, write `kanban/handoffs/<task-id>.<run-id>.json` containing the run's sanitized `metadata` dict augmented with `task_id`, `run_id`, `completed_at`, and `board` (the slug from `kanban/board.yaml`). Per-attempt naming mirrors the per-attempt `### Attempt N` subsections in step 6 — there is one JSON file per attempt, never overwritten. If a target file already exists with byte-identical content, skip silently (idempotent re-ingest). If it exists with **different** content, abort with: *"`kanban/handoffs/<task-id>.<run-id>.json` already exists with different bytes — a Hermes run was retried in place. Investigate the run history before overwriting."* (Per-attempt naming makes this near-impossible in practice; the divergence-abort is a safety net, not a hot path.) **Do not proceed to step 6 until every completed run has a matching handoff file** — that is the new acceptance gate; the wiki's `## Implementation Evidence` and the on-disk handoff log must agree on attempt count.
5. **Locate the originating wiki page** from the task body's `@wiki-spec` tag or wiki backlink (normally `wiki/specs/<spec-slug>.md`). Cross-check against the handoff's `wiki_spec` field — they must agree; if they diverge, abort.
6. **Append `## Implementation Evidence`** to the target page. For multi-attempt tasks, emit one `### Attempt N: <outcome>` subsection per non-final run (with `retry_notes` and `blocked_reason`), then a final block with: run id, completion timestamp, assignee profile, `verification` command(s) + result, `changed_files`, `residual_risk`, `branch_head`, the relative path to the matching `kanban/handoffs/<task-id>.<run-id>.json`, and a one-paragraph summary. On re-ingest of a different run, append a new dated subheading rather than overwriting.
7. Update the target's frontmatter `updated` field and any `## Sources` row that points at the spec or concept.
8. **Verify zero dangling links — acceptance gate.**
9. Append a dated entry to `wiki/log.md` recording the run id, target page, verification outcome, attempt count, residual risk, and the per-attempt handoff file paths.

If the run failed, still ingest — mark the section `Result: failed` and quote the failure reason from the handoff. Documenting failures honestly is the point of [[concepts/living-documentation]].
